C03 — Část A: Zmapujte současnou realizaci jednoho scénáře

Úterní předstih / první část společného C03

Cíl

Pochopit, jak současná implementace skutečně realizuje jeden scénář z C02, a připravit ověřený AS-IS podklad pro návrh architektury.

V tomto průchodu se naučíte

  • sledovat scénář od specifikace až do konkrétního kódu;
  • rozlišit business krok od technických detailů implementace;
  • identifikovat části systému, které scénář realizují;
  • zjistit, kde je stav uložen a kde se rozhoduje o jeho změně;
  • dohledat, kde se v implementaci vynucuje business pravidlo / invariant;
  • identifikovat relevantní externí a perzistenční závislosti;
  • vytvořit jednoduchý AS-IS strukturální pohled podle skutečného kódu;
  • formulovat konkrétní architektonickou otázku založenou na evidenci.

Vycházíte ze Specification Baseline v0.2 a běžící aplikace z C02.

Použijte jeden scénář, který už máte ve v0.2. Doporučený je Confirm Reservation; pokud je pro váš tým architektonicky zajímavější schvalování, použijte příslušný scénář s approval.

Výstup Části A

Do docs/architecture-and-decisions.md vložte:

  1. odkaz na použitý scénář a související požadavky/pravidla;
  2. mapování hlavních kroků scénáře na konkrétní kód;
  3. mapování jedné důležité alternativní/chybové větve;
  4. seznam hlavních částí implementace, které scénář realizují;
  5. kde je stav uložen, kdo rozhoduje o změně stavu a kde se vynucuje jedno důležité pravidlo;
  6. relevantní externí/perzistenční závislosti;
  7. jeden AS-IS strukturální diagram;
  8. jednu konkrétní otázku pro další architektonický návrh.

A7. Nakreslete AS-IS strukturální diagram

Diagram má ukázat současnou realizaci zvoleného scénáře, ne cílový návrh.

Postup

  1. Nakreslete obdélník Application code.
  2. Dovnitř vložte 3–7 bloků z A4.
  3. Každý blok musí mít:

- název;

- krátkou roli v tomto scénáři;

- pokud jde o skupinu, uveďte pod diagramem konkrétní třídy/moduly, které obsahuje.

  1. Databázi a externí systémy nakreslete mimo Application code.
  2. Nakreslete pouze vazby, které jsou pro zvolený scénář skutečně použité.
  3. Každou důležitou šipku popište slovesem/operací: confirm, load/save Reservation, send notification, validate token, ...
  4. Směr šipky musí odpovídat skutečnému směru volání nebo závislosti.
  5. Nemíchejte bez vysvětlení jednu konkrétní třídu s celou vrstvou. Pokud používáte různé úrovně detailu, označte typ bloku (class, module, external system, database).

SWI C03 — Part A: Map the Current Realization of One Scenario

Tuesday early start / first part of the common C03

Goal

Understand how the current implementation actually realizes one C02 scenario and prepare a verified AS-IS basis for architecture design.

What you will learn

  • trace a scenario from the specification into concrete code;
  • distinguish business-significant steps from technical implementation details;
  • identify the parts of the system that realize the scenario;
  • determine where state is stored and where state changes are decided;
  • locate where a business rule / invariant is enforced in the implementation;
  • identify relevant external and persistence dependencies;
  • create a simple AS-IS structural view based on the real code;
  • formulate a concrete architecture question supported by evidence.

Start from the Specification Baseline v0.2 and the running application from C02.

Use one scenario already present in v0.2. Confirm Reservation is recommended; if approval is more architecturally relevant for your team, use the corresponding approval scenario.

Part A output

Add to docs/architecture-and-decisions.md:

  1. reference to the selected scenario and related requirements/rules;
  2. mapping of the main scenario steps to concrete code;
  3. mapping of one important alternative/failure path;
  4. the main implementation elements that realize the scenario;
  5. where state is stored, who decides/executes the state change, and where one important rule is enforced;
  6. relevant external/persistence dependencies;
  7. one AS-IS structural diagram;
  8. one concrete question to carry into the architecture design.

A7. Draw the AS-IS structural diagram

The diagram shows the current realization of the selected scenario, not the target design.

Procedure

  1. Draw an Application code boundary.
  2. Place 3–7 elements from A4 inside it.
  3. Each block must contain:

- name;

- short role in this scenario;

- if it is a group, list the concrete classes/modules below the diagram.

  1. Draw the database and external systems outside Application code.
  2. Draw only dependencies/calls actually used by the selected scenario.
  3. Label every important arrow with an operation/verb: confirm, load/save Reservation, send notification, validate token, ...
  4. Arrow direction must match the real call/dependency direction.
  5. Do not mix a single class with an entire layer without explanation. If different abstraction levels are necessary, label the block type (class, module, external system, database).
